# Hydro-Agent 轻量水文世界模型（Hydro World Model）

**状态：** 首期设计契约  
**定位：** 为 `TaskState + EvidencePacket + Action Space` 增加稳定的水文领域语义层。  
**边界：** 本期不引入 RDF / OWL / SPARQL / Neo4j，不建设通用水利知识图谱，不改变现有 A01—A12 的执行逻辑。

---

## 1. 为什么需要这一层

当前 Hydro-Agent 已经具备任务状态、方案、数据快照、预报、证据、动作和权限，但 `basin_id`、`model_id` 等仍主要是运行标识。Agent 能知道“任务发生了什么”，但对“正在操作的水文世界”缺少统一、显式、可验证的对象模型。

本特性增加一个轻量 **Hydro World Model**，统一表达：

- Agent 正在处理哪个流域和站点；
- 当前可用的数据、forcing、状态和方案是什么；
- 哪个模型生成了哪个预报；
- 哪条证据支持或削弱哪个问题假设；
- 当前对象允许执行哪些动作；
- 一次动作如何产生新的证据并更新任务状态。

它不是额外的知识图谱产品，而是 Agent 的领域状态契约。

---

## 2. 设计原则

1. **轻量优先。** 首期使用 Pydantic / JSON Schema / SQLite 即可实现。
2. **对象稳定、关系显式。** 不依赖 Prompt 临时解释 `basin_id`、`scheme_id` 的语义。
3. **数值计算仍由确定性程序完成。** World Model 只组织状态和语义，不替代 XAJ、OpenHydroNet、Evaluator 或 Optimizer。
4. **Action 受约束。** Agent 只能选择对象、阶段、模型能力和预算共同允许的动作。
5. **证据驱动更新。** Tool Output 必须形成 EvidencePacket，再更新 World State / TaskState。
6. **可追溯。** 每个对象和关系都必须能回到数据快照、方案版本、动作运行或产物引用。
7. **不提前泛化。** 首期只支持“单流域、单模型、lead 1/2/3 历史起报回放”所需对象。

---

## 3. 核心对象

首期定义 10 个稳定对象类型。

| Object | 作用 | 首期最小字段 |
|---|---|---|
| `Basin` | 流域实体 | `basin_id`, `name`, `area_km2?` |
| `Station` | 水文/气象观测点 | `station_id`, `name`, `station_type`, `basin_id` |
| `DataSnapshot` | 某次任务可见的数据快照 | `snapshot_id`, `source`, `available_at`, `hash`, `variables` |
| `Forcing` | 模型驱动信息 | `forcing_id`, `snapshot_id`, `mode`, `issue_time`, `horizon` |
| `HydroState` | 某个起报时刻的水文上下文 | `state_id`, `basin_id`, `issue_time`, `current_flow?`, `antecedent_rainfall?`, `quality_flags` |
| `HydrologicModel` | 模型及能力注册 | `model_id`, `version`, `capabilities` |
| `Scheme` | 可执行预报方案 | `scheme_id`, `model_id`, `config_version`, `parameter_or_weight_ref`, `status` |
| `Forecast` | 一次预报产物 | `forecast_id`, `scheme_id`, `issue_time`, `lead_values`, `unit`, `artifact_ids` |
| `Evidence` | 工具返回的结构化证据 | `evidence_id`, `action_id`, `status`, `observations`, `metrics`, `gates` |
| `Task` | 一次预报方案构建任务 | `task_id`, `basin_id`, `phase`, `forcing_mode`, `current_scheme_id`, `terminal_status` |

说明：现有 `EvidencePacket` 即 `Evidence` 的运行时表示，不需要重新造一套平行结构。

---

## 4. 核心关系

关系不要求图数据库存储，首期可以直接通过外键 / ID 引用实现。

```text
Station        -- located_in ------> Basin
DataSnapshot   -- describes -------> Basin
Forcing        -- derived_from ----> DataSnapshot
HydroState     -- describes -------> Basin
Scheme         -- uses ------------> HydrologicModel
Forecast       -- generated_by ----> Scheme
Forecast       -- uses ------------> DataSnapshot
Forecast       -- starts_from -----> HydroState
Evidence       -- evaluates -------> Forecast / Scheme / DataSnapshot
Task           -- operates_on -----> Basin
Task           -- current_scheme --> Scheme
Task           -- accumulates -----> Evidence
```

关系的目的不是画图，而是保证 Agent 每次决策都能回答：

- 当前对象是谁；
- 数据从哪里来；
- 哪个方案用了哪个模型；
- 哪个预报基于哪个快照和状态；
- 哪条证据作用于哪个对象。

---

## 5. Action 与 World Model 的关系

现有 A01—A12 保持不变，但从“编号动作”进一步明确为对领域对象的受约束操作。

| Action | 主要读取对象 | 主要写入/产生对象 |
|---|---|---|
| A01 检查资料与预报条件 | `Task`, `Basin`, `DataSnapshot`, `Forcing` | `Evidence` |
| A02 有依据补取或纠正 | `DataSnapshot`, `Evidence` | 新 `DataSnapshot`, `Evidence` |
| A03 校验可执行方案 | `Scheme`, `HydrologicModel`, `Task` | `Evidence` |
| A04 重建起报条件 | `DataSnapshot`, `Scheme`, `Basin` | `HydroState`, `Evidence` |
| A05 执行预报 | `Scheme`, `HydroState`, `Forcing` | `Forecast`, `Evidence` |
| A06 诊断并建议下一动作 | `Task`, `Forecast`, `Evidence`, `HydroState` | 假设更新 / `Evidence` |
| A07 委托有限优化 | `Scheme`, `Evidence`, `HydrologicModel` | 候选 `Scheme`, `Evidence` |
| A08 Gate | 基础/候选 `Scheme`, `Forecast`, `Evidence` | ACCEPT / KEEP / ROLLBACK 证据 |
| A09 恢复、维持或受阻 | `Task`, `Evidence` | Task terminal / follow-up state |
| A10 冻结方案 | `Scheme`, `Task`, `Evidence` | frozen `Scheme` |
| A11 连续起报 | frozen `Scheme`, `DataSnapshot`, `HydroState` | `Forecast[]` |
| A12 只读评价与报告 | `Forecast[]`, observations | `Evidence`, report artifact |

## 6. 运行时世界状态

Agent 每轮不直接读取全部数据库，而读取一个面向决策的 `WorldStateView`。

```yaml
world_state_view:
  task:
    task_id: task-001
    phase: B
    forcing_mode: F

  basin:
    basin_id: "13235000"
    name: South Fork Payette River at Lowman

  hydro_state:
    issue_time: null
    current_flow: null
    antecedent_rainfall: null
    quality_flags: []

  model:
    model_id: xaj
    capabilities: [forecast, validate, calibrate]

  scheme:
    scheme_id: scheme-v1
    status: candidate

  forecast_summary:
    available: false
    lead_metrics: {}

  evidence_summary:
    supported: []
    weakened: []
    unresolved: [DATA, TIMING, STATE, FORCING, MODEL]

  permissions:
    safe_actions: [A01, A03]

  budget:
    agent_rounds_remaining: 20
    optimization_cycles_remaining: 4
```

`WorldStateView` 是投影，不是新的事实源。真实数据仍来自 Task / Scheme / Snapshot / Forecast / Evidence 等对象。

## 7. Agent 决策闭环

引入 World Model 后，现有 Agent Loop 的语义变为：

```text
Hydro World State(t)
        ↓
Build WorldStateView
        ↓
Agent 选择一个合法 Action
        ↓
Permission Gate
        ↓
Hydrology Tool / Numerical Model
        ↓
EvidencePacket + Artifacts
        ↓
Update Domain Objects / TaskState
        ↓
Hydro World State(t+1)
        ↓
Follow-up Gate
        └──── needs_follow_up=true ────> Agent
```

Agent 负责“下一步做什么”，不负责直接修改世界事实。

---

## 8. 权限模型

原有权限公式保留，并补充对象可执行性：

```text
allowed_actions =
  model_capability
  ∩ phase_permission
  ∩ task_permission
  ∩ strategy_registry
  ∩ remaining_budget
  ∩ object_preconditions
```

示例：

- 没有合法 `DataSnapshot` 时，不能执行 A05；
- `HydrologicModel.capabilities` 不含 `calibrate` 时，不能执行 XAJ 式率定；
- F/E 阶段即使模型支持优化，也必须拒绝 A07；
- 候选方案未通过 Gate 时不能 A10 freeze；
- 已冻结方案在 F 阶段不能被隐式修改。

这些规则必须由后端执行，不仅写在 Prompt 中。

---

## 9. 与现有 TaskState / EvidencePacket 的衔接

本特性不替换现有对象，而是整理它们的语义归属：

```text
TaskState
  = 当前 Task 的运行时控制状态

WorldStateView
  = Agent 每轮可见的领域状态投影

EvidencePacket
  = Action 对世界执行后的结构化观察

ActionLedger
  = 动作历史

Hydro World Model
  = 上述对象之间长期稳定的领域语义和关系契约
```

TaskState 保留：

- phase / forcing_mode；
- active_problem / hypotheses；
- attempted_actions / attempted_strategies；
- decision_round / optimization_cycle；
- budget；
- terminal_status。

World Model 补充：

- Basin / Station 的领域实体；
- Forcing / HydroState 的明确语义；
- Scheme → Model、Forecast → Scheme / Snapshot / State 的关系；
- Action 对对象的 precondition / effect。

## 11. 最小 API 契约

建议增加：

```python
get_world_state(task_id: str) -> WorldStateView

get_allowed_actions(task_id: str) -> list[ActionPermission]

apply_evidence(
    task_id: str,
    evidence_packet_id: str,
) -> WorldStateUpdate
```

注意：`apply_evidence` 不是让 LLM 自由写数据库，而是由确定性 updater 根据 EvidencePacket 进行受控更新。

---

## 12. 首期验收标准

该 feature 在实现阶段完成，当且仅当：

1. 10 个核心对象均有 schema；
2. 对象间关系可以通过 ID / 外键追溯；
3. 任意一次 `forecast` 能追溯到 `Task → Basin → Scheme → Model → DataSnapshot/HydroState → Forecast`；
4. 任意 EvidencePacket 能定位其 Action 和作用对象；
5. Agent 每轮通过 `WorldStateView` 获取领域状态，而不是依赖隐藏对话历史；
6. `get_allowed_actions()` 能根据 phase、模型能力、预算和对象前置条件过滤动作；
7. 不引入 RDF / OWL / 图数据库作为首期依赖；
8. 现有 A01—A12 和 B/F/E 语义保持兼容。

## 13. 课题表达方式

论文 / 答辩中建议称为：

> **轻量水文任务世界模型（Hydro World Model）**

而不是声称构建通用“水利行业本体”。

推荐描述：

> 本研究构建轻量水文任务世界模型，将流域、观测数据、气象驱动、水文状态、模型、预报方案、预报结果与证据统一组织为机器可解释的领域状态；智能体基于当前状态和工具返回证据，在受约束 Action Space 中动态选择下一操作。数值预测、参数搜索和评价仍由确定性水文模型与专业算法执行。

这样既吸收 Ontology / operational world model 的设计思想，又不把课题范围扩展为知识图谱研究。
