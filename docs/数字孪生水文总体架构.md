# Hydro-Agent 数字孪生水文总体架构

> 设计目标：参考水利水电工程数字孪生的分层思路，对当前课题进行**轻量化架构归位**，而不是建设完整生产级数字孪生平台。
>
> 本次重构遵循一个硬约束：**不改变当前 Hydro-Agent 的 A01—A12、WorldStateView、B/F/E 阶段权限、XAJ 计算链路和现有工作台运行方式。** 现有“五层一闭环”继续保留，但下沉为 Hydro-Agent 内部运行时架构。

## 1. 顶层定位

本课题的顶层架构调整为：

```text
                 智能业务应用
        预报 / 率定 / 诊断 / 方案 / 评价 / 报告
                         │
                         ▼
                 ┌──────────────┐
                 │ Hydro-Agent  │
                 │ 智能决策与编排 │
                 └──────┬───────┘
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     ┌─────────┐   ┌─────────┐   ┌─────────┐
     │ 模型平台 │   │ 知识平台 │   │ 数据底板 │
     └─────────┘   └─────────┘   └─────────┘
          │             │             │
          └─────────────┼─────────────┘
                        ▼
              Hydro Twin State / Evidence
                 版本 / 审计 / 追溯
```

这里的“平台”是**能力边界和接口抽象**，并不要求首期部署独立中间件或建设大型平台。

## 2. 数据底板

### 2.1 当前范围

首期只纳入本课题真实使用的数据：

- 水文资料：流量 Q；
- 气象/模型驱动：降水 P、PET/蒸散发相关输入及已接入 forcing；
- 空间资料：流域边界、GIS、DEM、站点；
- 流域属性：面积、高程等模型需要的静态属性；
- 模型运行产物：参数集、HydroState、Forecast、CalibrationResult、Metrics；
- 数据治理：DataSnapshot、source、available_at、valid_time、hash、版本和 lineage。

### 2.2 与现有实现的关系

当前 `Basin / Station / DataSnapshot / Forcing / HydroState` 等对象继续使用，不做破坏性修改。`DataSnapshot` 继续承担数据来源、版本、时间合法性和可追溯性的核心职责。

## 3. 模型平台

### 3.1 当前范围

模型平台不以模型数量衡量。首期即使主要只有 XAJ，也按统一能力接口组织：

```text
Model Registry
    └── XAJ

Model Capability
    ├── simulate / forecast
    ├── calibrate
    ├── validate / evaluate
    └── parameter / state artifacts
```

现有 XAJ Adapter、率定器、Optimizer、Evaluator 和 Model Registry 继续沿用。以后增加其他水文模型时，应通过相同的模型能力接口接入，而不是修改 Agent 主循环。

### 3.2 本次不改动

- XAJ 数值内核；
- 参数搜索算法；
- A05 Forecast、A07 Optimize、A08 Gate 等 Action 契约；
- 现有模型运行服务和工作台 API。

## 4. 知识平台

知识平台是本轮唯一需要实际调整运行依赖的部分。

### 4.1 V1 边界

当前仅建设两类知识：

1. **规范规则知识**：GB/T 22482—2026《水文情报预报规范》的课题相关条款及可执行评定参数；
2. **项目策略知识**：Hydro-Agent 科研任务自己的 Gate 策略。

暂不建设：

- 专家经验库：当前没有经过验证的真实预报员经验，先留接口，不编造；
- 知识图谱：暂不引入 Neo4j/图数据库；等后续形成“现象—假设—水文过程—参数组—动作—结果”真实案例后再决定是否图谱化；
- 大模型蒸馏：等积累真实、可验证的率定决策轨迹后再做。

### 4.2 为什么标准不能继续写在 Gate 代码里

标准、项目策略和程序逻辑是三种不同职责：

```text
标准知识：什么叫甲/乙/丙、什么是许可误差
                  ↓
确定性评定器：按照标准知识进行计算
                  ↓
评定报告：Scheme Grade / QR / DC / GRD / Evidence
                  ↓
项目 Gate 策略：本科研任务在什么条件下 ACCEPT / KEEP / ROLLBACK
```

因此禁止形成：

```text
GateEvaluator
    if NSE >= 0.5:
        ACCEPT
```

也禁止：

```text
SKILL.md metadata 中写标准阈值
    ↓
直接成为 Gate 出口
```

标准阈值必须来自版本化知识库；Skill 只描述**什么时候应该调用这些知识和工具**。

### 4.3 V1 知识流

```text
GB/T 22482—2026 原始标准
        │
        │ 人工审核后的结构化抽取
        ▼
knowledge/data/standards/gbt-22482-2026.json
        │
        ├── rules[]             条款知识
        └── profiles[]          可执行评定配置
        │
        ▼
KnowledgeRepository
        │
        ▼
GbtAccuracyConfig
        │
        ▼
确定性 GB/T Evaluator / LangGraph 子图
        │
        ▼
GbtAccuracyReport + provenance
        │
        ▼
GateEvaluator
        │
        ├── 有标准评定报告 → 按科研 policy 判定
        └── 无标准评定报告 → KEEP，不允许 NSE fallback ACCEPT
```

这里不采用“PDF → RAG → LLM → Gate”的方式。影响接受/回滚的规则必须经过结构化、版本化和确定性执行，LLM 可以检索和解释规范，但不能临时改写阈值。

### 4.4 标准与科研策略分离

GB/T 22482—2026 中的精度等级是**标准知识**；“本课题候选方案至少丙级才允许进入下一阶段”则是**科研策略**，两者不能混成一份代码常量。

V1 使用：

```text
knowledge/data/standards/gbt-22482-2026.json
knowledge/data/policies/hydro-agent-research-v1.json
```

标准文件负责：

- 条款号；
- 规范版本；
- 发布/实施时间；
- DC/QR 等评定分级；
- 洪峰、峰现、GRD、时效等当前课题使用的评定配置。

科研策略负责：

- `min_scheme_grade`；
- 是否必须存在 GB/T 评定报告；
- 标准报告缺失时是 KEEP 还是其他状态。

### 4.5 2026 版标准的时间状态

GB/T 22482—2026 已发布，但实施日期为 2027-02-01。因此本课题可以把它作为**研究目标规范/预发布知识版本**进行实验，但所有 provenance 必须保留 `published_on`、`effective_from` 和 `status`，不能表述成当前生产业务已经按 2026 版正式执行。

## 5. Hydro-Agent 内部运行时架构保持不变

原“五层一闭环”不删除，而是明确为 Agent 内部架构：

```text
Hydro World State
      ↓
WorldStateView
      ↓
Agent Observe + Decide
      ↓
Permission / Data Availability Gate
      ↓
Action Router
      ↓
Hydrology Tool / Numerical Model / Knowledge Evaluator
      ↓
EvidencePacket + Artifact
      ↓
Deterministic State Update
      ↓
Hydro World State(t+1)
```

所以本轮架构调整是**重新归位，不是重写系统**。

## 6. Hydro World Model 的新定位

现有 Hydro World Model 建议在顶层叙事中改称 **Hydro Twin State / Hydro Domain Model**，用于表达：

- Basin；
- Station；
- DataSnapshot；
- Forcing；
- HydroState；
- HydrologicModel；
- Scheme；
- Forecast；
- Evidence；
- Task。

它是 Agent 对数字孪生水文状态的统一认知契约，不等于“模型平台”，也不等于“知识图谱”。代码对象暂时无需重命名。

## 7. 本轮改造边界

本轮允许修改：

- 新增轻量 `knowledge` package；
- GB/T 22482—2026 规则结构化入库；
- 标准评定配置改由 KnowledgeRepository 提供；
- Skill 从“标准参数存储处”降为“知识使用说明”；
- A08 缺少标准评定报告时禁止通过硬编码 NSE fallback ACCEPT；
- 新增知识平台单元测试和架构文档。

本轮禁止修改：

- A01—A12 Action Space；
- Agent Loop；
- WorldStateView；
- B/F/E 权限；
- DataSnapshot 规则；
- XAJ 计算、率定和候选生成算法；
- 前端交互流程。

## 8. 后续演进

当真实运行积累了足够 Evidence 后，再逐步增加：

```text
Knowledge Platform V1
规范规则 + 项目策略
        ↓
V2
历史率定案例库
        ↓
V3
现象—过程—参数—动作关系图
        ↓
V4
经过验证轨迹训练/蒸馏的 Hydrologist Policy Model
```

核心原则不变：**规则来自知识平台，计算来自专业模型，决策来自 Agent，所有结果回到 Evidence。**
